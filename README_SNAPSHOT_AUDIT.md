# 演练策略快照的最早分歧——离线合成快照对照

仅依赖 **Windows 原生 Python 3.12 标准库**（hashlib/json/os/dataclasses/ast/subprocess…），
无第三方包、无网络。解决的问题：同一份合成配置在两个测试会场以**不同顺序**导入，
当前画面相同，但审查报告缺少"历史一致"的证据。

## 1. 它给出什么

| 结论 | 含义 |
|---|---|
| `equivalent` | 每个批准版本逐版本证毕一致（根哈希 + 画面摘要双证据） |
| `divergent` | 存在**已证**分歧，报告取**最早**的一个，并附双方摘要证据 |
| `inconclusive` | 存在**缺段**：从缺段批准版本起，版本链断裂，其后历史一致性**未证** |

"当前画面相同"与"历史一致"被严格区分：场景 2 演示了画面相同但历史分歧，
仍判 `divergent`；缺段时报告会列出每个缺口缺哪些分片、拒收留痕以及
`unproven_from`（从哪个批准版本开始的结果还未证）。

## 2. 目录结构

```
snapshot_audit/
  model.py    规范化 SHA-256、事件/批次/分片/批准清单/版本信封/回滚记录
  store.py    仅追加 pack 的内容寻址不可变存储（索引可删可重建，blob 自验）
  treap.py    持久化哈希 Treap：优先级仅由键哈希决定，与导入顺序无关
  venue.py    会场：分片装配、水位、信封链、历史读者 ReaderAt、受控回滚
  compare.py  对照器：按批准版本对齐，最早已证分歧 + 缺段未证清单
standalone_verifier.py  独立验证器（不 import 引擎、不读内部索引，含 AST 自检）
tests/test_exhaustive.py  小输入全枚举
tests/test_stress_50k.py  5 万条规则修订压力实测
run_demo.py    四个端到端场景
smoke_check.py 冒烟检查
```

## 3. 关键设计如何对应题面要求

1. **不同导入顺序、当前画面相同 ⇒ 同根哈希**。哈希 Treap 的节点优先级
   `prio = SHA256(key)`，与到达顺序无关；纯函数式更新（复制路径、复用旧子树），
   相同键值集合必然得到相同根。全枚举测试穷举 6 键 720 排列与 4 批次 24 顺序。
2. **事件批次可拆分**。`build_batch` 切分片，每片内容摘要写进**批准清单**的
   `fragment_digests`；会场可乱序、重复、部分接收分片，清单承诺的分片未收齐
   时批次永不提交。篡改分片在投递时即被摘要比对拒收并留痕。
3. **回滚必须引用批准的版本及范围**。`RollbackRecord(target_version, scope)`
   两者都校验：目标版本必须在已批准信封链上、范围非空；只对范围内的键生成
   补偿事件，产生**新信封**，历史信封与旧快照一律不删。
4. **历史读者只按水位见到完整批次**。提交以批次为原子单元，一个批次对应一个
   信封；`ReaderAt(water_mark)` 只能解析到该水位的根，半批在任何水位都不可见。
5. **最早的已证分歧 + 缺段未证**。对照器按批准版本号形成共同逻辑序列，
   链断裂后不再做根对齐，`proven_through` / `unproven_from` 明确可证边界。
6. **不依赖对照器内部索引的验证器**。`standalone_verifier.py`：
   - AST 自检（`--self-check`）证明不 import 引擎包、不引用存储索引文件名；
   - 自行顺序扫描全部 pack、按记录内摘要重建映射；
   - 用普通 `dict` 重放事件、按负载结构泛化遍历快照树（顺带复核 Treap 堆性质
     与"优先级仅由键决定"）；
   - 独立推导分歧/缺段/裁决，再与引擎报告交叉核对；
   - 退出码：0 一致 / 3 分歧 / 4 缺段未证 / 2 篡改或自相矛盾。
7. **5 万条互不相干规则修订实测**（`tests/test_stress_50k.py`）：
   100 批 × 5 分片，A 正序 B 逆序；实测补单批访问节点（O(log n) 量级）、
   冷态全量重建访问节点（O(n) 量级）、根摘要零访问比较、旧快照抽样保持、
   关闭重开后旧根可读、独立验证器两档裁决。结果写入 `artifacts/stress_result.json`。

## 4. 运行方式

```bat
python run_all.py                                  REM 一键：自检+全枚举+5万压测+演示
python run_demo.py
python -m unittest tests.test_exhaustive -v
python tests\test_stress_50k.py
python standalone_verifier.py --self-check
python standalone_verifier.py <会场A目录> <会场B目录> --history full --out verdict.json
```

会场目录即 `PackStore` 的存储路径（含 `blobs\pack-*.rec` 与 `venue_state.json`）。
`--history full|sample:N|none` 控制快照树逐信封核验密度，压测可用抽样档。

### 跨导入顺序如何对齐（集合见证）

信封版本号是会场本地序号，逆序导入时不能按版本号直接对齐。对照器与验证器
都采用同一判据：以每个信封的**已应用批准版本集合**为对齐键。顺序无关性
保证"同集合 ⇒ 同根"，因此：

- 两会场共同见证的集合，直接互相比根/画面摘要；
- 单方见证的集合，用严格按批准版本顺序的**规范重放**复核该方自身；
- 若不同批次对同一键有冲突值，逆序导入得到的画面会与规范重放不符，
  被正确判为已证分歧（这正是"当前画面可能相同、历史却不一致"的来源）。

## 5. 证据链一览

- 每条记录：`{"d": SHA256(规范化负载), "b": 负载}`，读取即自验，字节篡改必现；
- 信封链：版本连续 + 父指针 + 根哈希 + 画面摘要，全部内容寻址；
- 批准清单：分片摘要承诺 + 完整事件序列摘要，回滚/缺段/篡改均可追溯；
- 报告自身也有内容摘要（`ComparisonReport.content_digest()`）。
